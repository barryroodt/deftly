# Claude Code Extensions Adapter

## What this produces

Claude Code-specific artifacts inside an existing workspace that already
has `AGENTS.md` + `.agents/skills/`:

- `.claude/settings.json` — allow/deny lists + Agent Teams env flag
- `.claude/settings.local.json` — empty personal-overrides shell (gitignored)
- `.claude/CLAUDE.md` — bridge file importing `AGENTS.md` so CC reads
  the canonical workspace doc
- `.claude/skills/` — bridge (symlink, fallback to copy) to
  `.agents/skills/` so CC's skill discovery finds the same set
- `.gitignore` additions for `.claude/settings.local.json` and
  `CLAUDE.local.md`

**Not for:** Generating cross-agent workspace structure. That's the
core skill's job. This adapter only adds the CC-specific layer.

## Prerequisites

- `{workspace}/AGENTS.md` exists (written by core Step 2.9)
- `{workspace}/.agents/skills/` populated (written by core Steps 2.6-2.8)
- Tech-stack table + user permission answers from core Step 2.5 are
  available (passed in by the core skill)

## Anti-Patterns

- **NEVER blind-write `.claude/settings.local.json`** — the Claude Code
  harness auto-creates this file with session permissions. Clobbering
  wipes them silently. Always read first; if non-empty, merge or skip.
- **NEVER commit `.claude/settings.local.json`** — it carries personal
  overrides (local MCP servers, experimental flags). Confirm the file
  appears in `.gitignore` before any `git add`.
- **NEVER duplicate `AGENTS.md` content into `.claude/CLAUDE.md`** —
  use the `@AGENTS.md` import pattern (or a symlink). Duplicating
  guarantees drift between the canonical doc and the CC-visible copy.
- **NEVER write `.claude/settings.json` without merging tech-stack and
  user-answer rules** — the file is the union of base allow rules,
  detected-stack rules from core Step 2.4, and user deploy-denials +
  WebFetch/MCP allows from core Step 2.5.
- **NEVER set `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` if the team
  skill was not generated** — core Step 2.8 only generates
  `.agents/skills/team/SKILL.md` when CC is a target. The env flag
  is harmless on its own, but turning it on without the skill confuses
  users.

## Step 1: Generate settings.json

**MANDATORY — load `references/templates/settings-json.md` before writing.**

Write `{workspace}/.claude/settings.json` from the template base. Merge
in this order (later wins on duplicates):

1. Base allow + deny lists from the template
2. Tech-stack allow rules from the core skill's Step 2.4 detection
3. User deploy-command denials gathered in core Step 2.5
4. User WebFetch domains and MCP server patterns from core Step 2.5

Keep `env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS = "1"`. The team skill
is generated by core only when CC is selected (gated in core Step 2.8),
so the flag is always valid here.

## Step 2: Generate settings.local.json (read-first)

Before writing, check if `{workspace}/.claude/settings.local.json`
already exists:

- If absent: write `{}` (empty JSON object).
- If present and equals `{}`: leave untouched.
- If present and non-empty: do NOT overwrite. The CC harness has
  written session permissions there. Inform the user; skip this step.

## Step 3: Generate CLAUDE.md bridge

CC does not read `AGENTS.md` natively (verified — see core
`references/agent-paths.md` Q1). Write a one-line bridge at
`{workspace}/.claude/CLAUDE.md` (or `{workspace}/CLAUDE.md` — CC accepts
both; prefer `.claude/CLAUDE.md` to keep workspace root tidy):

```
@AGENTS.md
```

The `@<path>` syntax tells CC to import the referenced file at session
start. This keeps `AGENTS.md` as the single source of truth — no copy
drift.

Alternative (POSIX only, no Windows support): a symlink

```bash
ln -s ../AGENTS.md {workspace}/.claude/CLAUDE.md
```

Prefer the `@AGENTS.md` import. Use the symlink only if the user
specifically requests no import directive in CLAUDE.md.

## Step 4: Generate .claude/skills/ bridge

CC's skill discovery walks `.claude/skills/<name>/SKILL.md`, not
`.agents/skills/`. Create a bridge so the same skill set is visible to
CC without duplication.

Preferred: symlink the entire directory.

```bash
ln -s ../.agents/skills {workspace}/.claude/skills
```

Verify the symlink target resolves (`ls {workspace}/.claude/skills/`
should list the skill directories created by core Step 2.6-2.8).

Fallback (no symlink support, e.g. Windows without dev-mode):
copy the directory tree. Document in the workspace `AGENTS.md`
"Workspace Rules" section that regenerating skills requires re-running
this adapter or manually re-copying.

```bash
cp -R {workspace}/.agents/skills {workspace}/.claude/skills
```

## Step 5: Append .gitignore entries

Append CC-specific personal-overrides lines to `{workspace}/.gitignore`
(do not clobber — read existing, append the new section):

```
# Claude Code personal overrides (not committed)
.claude/settings.local.json
CLAUDE.local.md
```

If the lines already exist (re-running adapter), skip.

## Step 6: Verification

Confirm all CC-adapter artifacts exist and resolve correctly:

```bash
test -f {workspace}/.claude/settings.json
test -f {workspace}/.claude/settings.local.json
test -f {workspace}/.claude/CLAUDE.md   # or test -L for symlink mode
test -L {workspace}/.claude/skills || test -d {workspace}/.claude/skills
# Skill discovery sanity:
ls {workspace}/.claude/skills/architect/SKILL.md
```

If `claude-code` is the only target, the team skill is required too:

```bash
ls {workspace}/.claude/skills/team/SKILL.md
```

If `team` is missing but `claude-code` was selected, this is a bug in
core Step 2.8 — flag to the user.

## Step 7: Hand back to core

Return control to the core scaffold skill with a summary:

- Files written / skipped (with reasons)
- Whether `settings.local.json` was preserved or freshly created
- Whether CLAUDE.md uses `@import` or symlink
- Whether skills bridge is symlink or copy

The core skill records this in its Phase 3.5 final verification table.
